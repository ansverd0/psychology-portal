# SPEC: «Практикум» — задания на компетентность (таксономия Блума)

> Версия 0.1 от 2026-11-12. Общий контракт для бэкенда и фронтенда.
> Замораживается до старта сбора данных 17.11.2026: после начала сбора
> названия уровней, события и метрики не меняются.

## 1. Зачем

Сейчас портал закрывает нижние уровни: карточки — «запоминание», статьи и
билеты — «понимание», тесты — в основном «понимание». Заданий на
«применение», «анализ», «оценку» и «создание» нет. Из-за этого:

- студент не проверяет, умеет ли он действовать, а не только узнавать;
- исследование видит только репродуктивную подготовку;
- разговор о «полном учебном цикле» остаётся декларацией.

«Практикум» добавляет квазипрофессиональные задачи верхних уровней. Это не
замена практике и не измерение компетентности: портал даёт задачу, критерии
и эталон для самопроверки, а исследование фиксирует **работу с задачей**, а
не уровень сформированности компетентности.

## 2. Термины

- **Компетенция** — нормативное требование из ОПОП/ФГОС (что должно быть
  освоено). Задаёт рамку.
- **Компетентность** — реальная способность действовать в профессиональной
  ситуации. Проверяется задачей, а не тестом на узнавание.
- **Уровень Блума** — уровень учебной цели (в редакции Андерсона и
  Кратволя, 2001): запоминание → понимание → применение → анализ → оценка →
  создание.

## 3. Уровни

| Код | Русская подпись | Что проверяет | Пример задачи |
|---|---|---|---|
| `remember` | Запоминание | узнаёт термин, факт | не используется в практикуме |
| `understand` | Понимание | объясняет, классифицирует | не используется в практикуме |
| `apply` | Применение | применяет знание в ситуации | по жалобе выбрать методику и обосновать |
| `analyze` | Анализ | выделяет механизмы, сравнивает | сравнить две теории по критериям |
| `evaluate` | Оценка | обосновывает выбор, критикует | оценить валидность вывода |
| `create` | Создание | проектирует продукт | составить план консультации/заключение |

В БД допускаются все шесть кодов (на будущее), но в `practice.json` пилота —
только `apply`, `analyze`, `evaluate`, `create`. Фронтенд показывает фильтры
по тем уровням, которые реально есть в данных.

Порядок уровней для сортировки: `remember=1`, `understand=2`, `apply=3`,
`analyze=4`, `evaluate=5`, `create=6`.

## 4. Модель данных

### 4.1. `public.practice_tasks`

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | `bigserial` | PK |
| `discipline_id` | `text` | FK → `disciplines(id)`, `on delete cascade` |
| `slug` | `text` | `^[a-z0-9-]{3,64}$`, уникален внутри дисциплины |
| `level` | `text` | `remember|understand|apply|analyze|evaluate|create` |
| `competence` | `text` | код/формулировка из ОПОП, может быть null |
| `title` | `text` | 5–200 символов |
| `situation` | `text` | 50–5000 символов, HTML разрешён |
| `task` | `text` | 20–2000 символов, HTML разрешён |
| `kind` | `text` | `choice|open` |
| `options` | `jsonb` | для `choice`: массив 2–6 строк; для `open`: null |
| `correct_index` | `integer` | для `choice`: 0…длина options−1; для `open`: null |
| `criteria` | `jsonb` | массив 3–5 строк, каждая 10–300 символов |
| `model_answer` | `text` | для `open`: обязателен, 50–8000; для `choice`: может быть null |
| `explanation` | `text` | для `choice`: 20–2000; для `open`: может быть null |
| `source` | `text` | до 500 символов, откуда кейс/факты |
| `ai_generated` | `boolean` | default false |
| `active` | `boolean` | default true |
| `sort_order` | `integer` | default 0 |
| `created_at` | `timestamptz` | default now() |
| `updated_at` | `timestamptz` | default now(), обновляется триггером |

Уникальный ключ: `(discipline_id, slug)` — по нему идёт идемпотентный импорт.

Проверки (семантика, синтаксис можно уточнить):

- `kind = 'choice'` → `options` массив 2–6, `correct_index` в диапазоне,
  `explanation` заполнен.
- `kind = 'open'` → `options is null`, `correct_index is null`,
  `model_answer` заполнен.
- `criteria` — массив 3–5 строк.
- `level` — один из шести кодов.

### 4.2. `public.practice_attempts`

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | `bigserial` | PK |
| `user_key` | `text` | FK → `users_profiles(user_key)`, `on delete cascade` |
| `task_id` | `bigint` | FK → `practice_tasks(id)`, `on delete cascade` |
| `answer` | `jsonb` | объект: `{"choice": 1}` или `{"text": "..."}` |
| `self_score` | `smallint` | null для `choice`; 0…`max_score` для `open` |
| `max_score` | `smallint` | null для `choice`; `criteria.length * 2` для `open` |
| `is_correct` | `boolean` | null для `open`; для `choice` считает RPC |
| `duration_ms` | `integer` | 5000…7200000, может быть null |
| `created_at` | `timestamptz` | default now() |

Ограничения:

- `not (is_correct is not null and self_score is not null)`;
- `(self_score is null) = (max_score is null)`;
- `jsonb_typeof(answer) = 'object'`.

Индексы: `(user_key, created_at)`, `(task_id, created_at)`.

### 4.3. RPC

**`public.submit_practice_attempt(p_key text, p_task_id bigint, p_answer jsonb, p_self_score integer default null, p_duration_ms integer default null) returns jsonb`**

- `security definer`, `set search_path = public`;
- проверяет, что `p_key` есть в `users_profiles`;
- проверяет, что задача существует и `active`;
- `choice`: в `answer` есть числовой `choice`, индекс в диапазоне;
  `self_score` должен быть null; `is_correct` считается сравнением с
  `correct_index`;
- `open`: в `answer` есть строка `text` длиной 30–8000; `self_score` обязателен
  и 0…`criteria.length * 2`; `max_score` считается сервером;
- `duration_ms` проверяется, если передан;
- вставляет строку и возвращает
  `{"attempt_id": ..., "is_correct": true|false|null, "self_score": ..., "max_score": ...}`;
- при ошибке — `raise exception` с коротким кодом (`unknown user_key`,
  `unknown task`, `bad answer`, `bad self_score`, `bad duration`).

**`public.practice_progress(p_key text) returns table(task_id bigint, attempts integer, best_self_score integer, max_score integer, last_at timestamptz, last_is_correct boolean)`**

- `security definer`, проверяет ключ;
- агрегирует попытки по `task_id`: число попыток, лучший self-score, максимум,
  время последней, `is_correct` последней;
- нужен фронтенду для прогресса на другом устройстве; если RPC недоступен,
  фронтенд живёт на localStorage.

### 4.4. RLS и гранты

- `practice_tasks`: RLS включён; `select` для `anon, authenticated`; записи
  только через `service_role` (импорт). Политика `practice read`.
- `practice_attempts`: RLS включён; **никаких** политик для `anon`; запись
  только через RPC (SECURITY DEFINER). Прямой `insert/select` запрещён.
- `revoke all` на обе таблицы у `anon, authenticated`; затем `grant select` на
  `practice_tasks`.
- `grant execute` на обе RPC для `anon, authenticated`.
- Триггер `content_version_practice` на `practice_tasks` — как у остальных
  контентных таблиц.
- В конце миграции: `notify pgrst, 'reload schema';`.

## 6. UX

### 6.1. Страница

`practice.html`, `body data-page="practice"`.

- Шапка: «Главное меню», заголовок «Практикум», подпись
  «Задания на применение, анализ, оценку и создание».
- Двухколоночный макет как у `tests.html`: слева дисциплины и фильтр уровней,
  справа список задач / карточка задачи.
- Слева: прогресс «Пройдено X из Y», плитки дисциплин (только те, где есть
  задачи), чипы уровней «Все / Применение / Анализ / Оценка / Создание».
- Справа: список карточек (`data-practice-task`), у каждой — бейдж уровня,
  компетенция, заголовок, короткий фрагмент ситуации, статус.
- Карточка задачи: ситуация, задание, варианты или textarea, кнопка
  «Проверить» / «Показать критерии», после — результат, эталон, «Следующая».
- Мобильная версия: одна колонка, плитки дисциплин как в `tests.html`,
  без горизонтального скролла на 390 px.

Контракт для тестов (data-атрибуты, чтобы `ui-probe` не зависел от текста):

| Селектор | Что это |
|---|---|
| `#practice-app` | корень страницы |
| `[data-practice-discipline]` | плитка дисциплины |
| `[data-practice-level]` | чип уровня |
| `[data-practice-task]` | карточка задачи в списке |
| `[data-practice-task-view]` | открытая карточка задачи |
| `[data-practice-open-task]` | кнопка «открыть задачу» |
| `[data-practice-criteria]` | блок критериев/рубрики |
| `[data-practice-result]` | блок результата после попытки |
| `[data-practice-next]` | кнопка «следующая задача» |

### 6.2. Потоки

**Choice.** Открыл → выбрал вариант → «Проверить» → RPC → верно/неверно +
объяснение + эталон. События: `task_open`, `task_submit`.

**Open.** Открыл → написал ответ → «Показать критерии» → по каждому критерию
0/1/2 → «Сохранить попытку» → RPC → эталон + сравнение. События:
`task_open`, `self_check`, `task_submit`.

Критерии показываются **после** попытки ответить, чтобы не выдавать эталон
заранее; кнопка «Показать критерии» доступна и до, но с предупреждением
«сначала попробуйте ответить».

### 6.3. Гость и ключ

- Без `research_user_key` чтение и прохождение доступны, но попытка не
  сохраняется: показывается плашка «Создайте ID, чтобы сохранить попытку»
  и кнопка, вызывающая `openAuthModal()`.
- Если ключ есть — RPC вызывается; при ошибке ответ не теряется, показывается
  toast и кнопка «Повторить».
- Прогресс: `localStorage` `hub_practice_progress_v1`; при наличии ключа
  дополнительно `practice_progress` RPC, слияние по `task_id`.
- Черновик ответа: `hub_practice_draft_v1_<task_id>`, очищается после
  успешной отправки.

### 6.4. События

`PsyTracker.event(name, meta)`, `page='practice'` автоматически.

| Событие | Когда | `meta` |
|---|---|---|
| `task_open` | открыта карточка задачи | `task_id`, `slug`, `level`, `competence`, `kind` |
| `task_submit` | RPC вернул успех | `task_id`, `slug`, `level`, `competence`, `kind`, `correct` (choice), `self_score`, `max_score` (open) |
| `self_check` | сохранена рубрика open-задачи | `task_id`, `level`, `self_score`, `max_score` |

`meta` должен быть коротким: без текста ответа и без ФИО.

## 7. Метрики исследования

Считаются на выгрузке, не в момент записи.

| Метрика | Формула | Зачем |
|---|---|---|
| `practice_users` | число уникальных `user_key` с попытками | охват |
| `practice_attempts` | число строк `practice_attempts` | активность |
| `higher_order_share` | время/события на `practice` ÷ всё учебное время/события | выход на верхние уровни |
| `level_mix` | доля попыток по `level` | какие уровни выбирает |
| `self_score_avg` | средний `self_score / max_score` по open | самооценка результата |
| `return_after_low_score` | `self_check` с низким баллом → повторное `task_open`/`task_submit` в течение N минут | регуляторный возврат |
| `time_by_level` | dwell/интервалы по уровням | сколько времени на верхних уровнях |

Гипотеза: высокие `planning`, `modeling`, `programming`, `results` (ССПМ)
связаны не с общим временем, а с `higher_order_share`, завершением задач
верхних уровней и возвратом после низкой самопроверки. Низкая саморегуляция —
с пребыванием в карточках/билетах и редким выходом на `apply+`.

Ограничение: `practice_attempts` — поведенческий индикатор работы с задачей,
а не измерение компетентности. Это фиксируется в главе 2 и в отчёте.

## 8. Правила контента

- Задача — квазипрофессиональная: жалоба, протокол, случай, вывод, запрос.
- `criteria` — 3–5 наблюдаемых признаков, не «правильно/неправильно».
- `model_answer` — эталон, а не единственно возможный ответ; для open
  допускает альтернативы.
- `explanation` для choice — почему верный вариант верен, а остальные нет.
- `source` — реальный источник или раздел портала; не выдумывать.
- `ai_generated: true`, если текст писался моделью; на странице — плашка.
- Не указывать ФИО, группы, реальные случаи, по которым можно опознать
  человека.
- Не делать выбор из 2 вариантов «да/нет» и «все вышеперечисленное».
- Один уровень — одна задача; не смешивать `apply` и `create` в одной.

## 10. Вне рамок

- Автоматическая проверка открытых ответов и «оценка компетентности».
- Экспертная валидация заданий.
- Блокировка контента, геймификация, рейтинги.
- Новые фреймворки/сборщики.
- Переразметка существующих тестов по уровням (можно позже).
