## 4. Шесть первопричин

1. **Данные = сеть.** Контент страниц приходит только из Supabase; нет ни скелетона, ни ошибки, ни ретрая. Отсюда пустой tickets на телефоне и «выберите дисциплину слева» там, где слева ничего нет.
2. **Ложный офлайн.** Любая сетевая ошибка трактуется как «нет интернета». При заблокированном/медленном Supabase пользователь видит «Работаем в автономном режиме», хотя сеть есть.
3. **Закладки живут в трёх местах.** Список в панели, список в модалке и звезда в статье обновляются независимо — рассинхрон неизбежен (звезда не гаснет, заголовок дублируется).
4. **Брейкпоинты не согласованы.** Колонки навигации, панель закладок, FAB и поиск включаются/выключаются на разных ширинах; в зазоре 769–1120 нет доступа к закладкам, а поиск зажат в 120 px.
5. **Плавающие кнопки без общей сетки.** FAB, «наверх» и тултип имеют разные `z-index`, разные отступы и высоты — перекрывают друг друга, подвал и подсказки.
6. **Кэш сильнее релиза.** `cache-first` для статики + версия SW: исправления доходят не сразу, а «сломанное» остаётся у пользователя.

### Фаза 1. Данные и офлайн

#### U2-01 · Не показывать «автономный режим», когда сеть есть — P0, 0,3 дня

**Симптом (news):** «страницы выдают офлайн-плашку при подключении через Wi-Fi, VPN не ухудшает работу, даже наоборот».

**Причина:** `js/supabase-config.js:421-424` ловит любую ошибку загрузки и вызывает `activateLocalDatabaseFallback()`, а тот безусловно вызывает `showOfflineNotification()` (`:182`). Ошибка может быть таймаутом 12 с, 500-й, блокировкой домена — всё равно «Работаем в автономном режиме».

**Что сделать:**

1. Ввести два разных сообщения:
   - **нет сети** (`navigator.onLine === false`) → текущая плашка «автономный режим»;
   - **сеть есть, облако недоступно** → тихий тост/строка «Не удалось обновить материалы. Показаны сохранённые» + кнопка «Повторить», без слова «офлайн».
2. Не показывать ничего, если данные взяты из кэша и ему меньше суток (пользователю нечего делать с этой информацией).
3. Писать причину в `logs/` (см. дисциплину проекта) — сейчас только `console.warn`.

**Приёмка:** при заблокированном `*supabase.co` и живом `navigator.onLine` плашки «автономный режим» нет; при выключенном Wi-Fi — есть.

#### U2-02 · Пустые данные: скелетон, ошибка, ретрай вместо тупика — P0, 0,6 дня

**Симптом (tickets, моб.):** поиск есть, ниже пусто, в блоке контента — «Выберите экзаменационную дисциплину слева…», хотя слева на телефоне ничего нет. Воспроизведено при блокировке Supabase: 0 плиток, 0 папок, та же заглушка.

**Причина:** `initTickets` (`js/tickets.js:6-7`) и `initSections` (`js/sections-wiki.js:7`) молча выходят, если данных нет. Заглушки в HTML статичны и написаны под ПК.

**Что сделать:**

1. Разделить три состояния: **загрузка** (скелетон плиток/списка), **пусто из-за ошибки** (карточка «Не удалось загрузить билеты» + «Повторить» + ссылка «Главное меню»), **пусто по-настоящему** (текст, зависящий от ширины: «Выберите дисциплину выше» на телефоне).
2. Ретрай без перезагрузки: повторный вызов загрузчика для текущей страницы, обновление кэша, перерисовка.
3. Сократить `SUPABASE_TIMEOUT_MS` с 12 000 до 6 000 для первого экрана: 12 с пустого экрана на мобильной сети — это и есть «не загружается».
4. Если кэш есть — рисовать его сразу (уже так) и не стирать при неудачном обновлении (проверить, что `savePageCache` не вызывается с пустым payload).

**Приёмка:** при блокировке Supabase и пустом localStorage tickets показывает карточку ошибки с работающей кнопкой «Повторить»; после снятия блокировки повторный клик рисует плитки без перезагрузки страницы.

#### U2-17 · Опрос на телефоне без VPN — P1, 0,3 дня (сначала данные)

**Симптом:** «на телефоне не загружается без VPN».

**Что известно:** при заблокированном Supabase страница опроса отрисовалась (первый экран, 970 символов) и баннер не появился. То есть воспроизвести «белый экран» блокировкой домена не удалось.

**Что сделать:** получить с устройства автора: скриншот, `chrome://net-export` или хотя бы «что именно видно» (белый экран / спиннер / ошибка). До этого кода не трогать — иначе лечим симптом наугад. Параллельно добавить на survey.html обработчик `window.onerror` с текстом «Не удалось запустить опрос» — он полезен в любом случае.

**Приёмка:** есть лог/скриншот с телефона и названная причина; либо зафиксировано «не воспроизводится».

### Фаза 2. Закладки

#### U2-03 · Одно состояние закладок на все точки — P1, 0,4 дня

**Симптомы:** (а) удалил закладку крестиком в правой панели — звезда в статье осталась жёлтой; (б) в мобильной модалке после удаления появляется второй заголовок «⭐ Закладки».

**Причины:** (а) `js/bookmarks.js:135-142` перерисовывает только панель; обработчик звезды (`js/tickets.js:277-282`, `js/sections-wiki.js:359-364`) обновляет только себя; (б) рекурсивный вызов `renderBookmarksPanel(container, type, onItemClick)` на `js/bookmarks.js:140` не передаёт `options`, и `showHeading` снова становится `true` (`:100`).

**Что сделать:**

1. Одна точка правды: `removeBookmark/addBookmark` шлют `document.dispatchEvent(new CustomEvent('bookmarks:changed', { detail: { type, id } }))`.
2. Звезда получает `data-bookmark-type` и `data-bookmark-id`; подписчик `syncBookmarkStars()` пересчитывает `active`/`★` для всех таких кнопок. Это же чинит сценарий «удалил в модалке — погасло в статье».
3. В обработчике удаления передавать `options` дальше: `renderBookmarksPanel(container, type, onItemClick, options)`.
4. Счётчик FAB обновлять из того же события, а не только из `saveBookmarks`.

**Приёмка:** удаление из панели и из модалки гасит звезду и уменьшает счётчик без перезагрузки; в модалке ровно один `<h3>` после любого числа удалений; `npm run check:ui -- bookmarks` подтверждает.

#### U2-04 · Закладки доступны на любой ширине — P1, 0,3 дня

**Симптом:** «пропадает возможность посмотреть закладки на нестандартной ширине окна».

**Причина:** 769–1120 px панель скрыта (`style.css:1560-1562`), FAB включается только ≤768 (`:1247`).

**Что сделать:** связать два правила одним брейкпоинтом: панель видна только там, где хватает места (≥1600 px после задачи U2-08), во всех остальных случаях показывать FAB. Не дублировать условие в двух медиазапросах — вынести в `@media (max-width: 1599px)`.

**Приёмка:** на 800, 1024, 1120, 1300, 1440 px список закладок открывается кнопкой; на 1600+ — правой колонкой; ни на одной ширине нет одновременно «ни панели, ни кнопки».

### Фаза 3. Мобильная навигация и кнопки

#### U2-05 · Плитки 3-в-ряд на телефоне — P0, 0,3 дня

**Симптом (sections, моб.):** «сломанная навигация по разделам. Для статей всё хорошо». На tickets то же: плитки 2+1, разной ширины (160/198/193 px).

**Причина:** `style.css:1355-1357` — правило `.limited-tiles > * { flex: 0 0 auto; }` (добавлено в раунде 1 против наложения заголовков) перебивает `flex: 1 1 calc(33.33% - 10px)` у `.mobile-tile-btn` (`:610-624`): специфичность равна, правило ниже в файле. Плитки перестают расти и переносятся по две.

**Что сделать:**

1. Убрать `.limited-tiles > *` из списка `flex: 0 0 auto`; оставить только списки-контейнеры (`.tickets-questions-column > *`, `.tickets-folders-column > *`, `.mobile-articles-container > *`) — там это действительно нужно.
2. Если плиткам всё же нужен запрет сжатия — задать его внутри `.mobile-tile-btn` после `flex`.
3. Проверить, что `max-height: 260px` у `.limited-tiles` не режет третью строку при 4+ плитках.

**Приёмка:** 390 px — три плитки в один ряд, равной ширины, третья не «висит» по центру; на 4+ дисциплинах работает вертикальный скролл, а не обрезка.

#### U2-06 · Кластер плавающих кнопок — P1, 0,4 дня

**Симптомы:** FAB перекрывает «Главное меню» в подвале (tickets/sections, моб.); кнопки «закладки» и «наверх» на разной высоте; вики-подсказка уходит под кнопки.

**Причины:** FAB — `left:16; bottom:16; 52px` (`style.css:1248-1251`), «наверх» — `right:30; bottom:30; 50px` (`:935-950`); `z-index` 9998 против 99999; тултип — 999 (`:516`).

**Что сделать:**

1. Общий контейнер/переменные: `--fab-size: 52px`, `--fab-gap: 12px`, `--fab-bottom: calc(16px + env(safe-area-inset-bottom))`. FAB — слева, «наверх» — справа, обе на одной линии `bottom`.
2. Подвал при видимом FAB (≤1599 px) получает `padding-bottom: calc(96px + env(safe-area-inset-bottom))`, чтобы кнопки не накрывали «Главное меню» и «Политику данных». Альтернатива — скрывать FAB, когда подвал в зоне видимости (`IntersectionObserver`), но padding проще и надёжнее.
3. Тултип `.wiki-term::after` — `z-index: 100001` (выше FAB и «наверх»), на мобиле уже `position: fixed` (`:687-694`) — оставить.

**Приёмка:** на 390 px внизу страницы видны и нажимаются обе кнопки подвала; FAB и «наверх» на одной высоте; подсказка термина целиком видна и не уходит под кнопки.

#### U2-11 · Убрать квадратную подсветку тапа — P2, 0,1 дня

**Симптом (news, моб.):** «убрать квадратное выделение как у текста с кнопок при нажатии».

**Что сделать:** глобально для интерактивных элементов:

```css
button, a, [role="button"], .mobile-tile-btn, .bookmark-star-btn {
    -webkit-tap-highlight-color: transparent;
    -webkit-touch-callout: none;
    user-select: none;
}
```

Не применять `user-select: none` к тексту статей и полям ввода. Для `:focus-visible` оставить видимую рамку — доступность не страдает, это разные механизмы.

**Приёмка:** на Android Chrome долгий тап по плитке не рисует серый прямоугольник; тап по тексту статьи по-прежнему выделяет слова.

#### U2-13 · Шапка на телефоне — P2, 0,2 дня

**Симптом:** «выровнять текст под „Ваш ID“».

**Что известно:** сейчас на 390 px h1 по центру, виджет ID по центру, подзаголовок слева — три разных выравнивания в одном экране.

**Что сделать:** выбрать одно правило для ≤768 и применить ко всем трём элементам: h1 слева, виджет под ним на всю ширину (ID — слева, «Выйти» — справа), подзаголовок слева. При активном ID строка не должна переноситься в две колонки.

**Приёмка:** при активном ID на 390 px подпись и кнопка «Выйти» на одной строке, левый край совпадает с левым краем заголовка; при гостевом состоянии — то же выравнивание.

### Фаза 4. ПК: ширина, колонки, поиск

#### U2-07 · Поиск: вынести из узкой колонки и научить искать по тексту — P1, 0,6 дня

**Симптомы:** «в поисковой строке не видно текста-подсказки», «не работает поиск», «слишком тесное окно поиска».

**Причина:** поле лежит внутри первой колонки навигации (`tickets.html:51-54`, `sections.html:50-53`) шириной 160–210 px; фактическая ширина поля — 120 px. Правило `style.css:872` (`display: block !important`) включает «мобильный» поиск и на ПК, но не меняет ему ширину. Список результатов — та же колонка 120 px (`:883-890`).

**Что сделать:**

1. Вынести разметку поиска из `<aside class="tickets-sidebar">` наверх `.nav-left` отдельным блоком, растянуть на обе колонки: `.nav-left { display: grid } .nav-search { grid-column: 1 / -1 }`. На мобиле визуально ничего не меняется — поиск и так первый.
2. Ширина поля ≥ 320 px; выпадашка — `min-width: 360px`, при нехватке места прижимается к правому краю; `max-height: 50vh`.
3. Искать по названию **и** тексту конспекта: один раз при инициализации собрать `haystack = title + ' ' + textContent(content)`; совпадение — подсвечивать сниппет (40–60 символов вокруг).
4. Мелочи, без которых поиск «не работает»: debounce 150 мс, минимум 2 символа, «Ничего не найдено» с подсказкой, счётчик результатов, `Esc` закрывает, стрелки ходят по списку, `Enter` открывает первый.
5. Ограничить выдачу 30 результатами + «показать все».

**Приёмка:** при 1440 px поле ≥ 320 px и placeholder виден целиком; «память» находит вопросы по тексту; клик открывает билет и прокручивает к просмотрщику; `Esc` и клик мимо закрывают список.

#### U2-08 · Ширина контента и колонок — P1, 0,6 дня

**Симптомы:** «расширить блок контента, если экран позволяет», «немного расширить колонки навигации».

**Причина:** просмотрщик ограничен 780 px (`style.css:1075-1080`), контейнер — 1640 px (`:1013-1024`), колонки на 769–1499 — 160/210 (`:1542-1545`). Замеры текущей сборки: просмотрщик 523 px на 1280, 683 px на 1440, 780 px на 1920 — при том, что панель закладок занимает 240 px.

**Что сделать:**

1. Сетка-токены: `--nav-a: 170px; --nav-b: 220px; --viewer-max: 900px; --layout-max: 1760px`.
2. Показывать правую панель закладок только с 1600 px (после U2-04); ниже — FAB. Это отдаёт контенту 240 px на типичных ноутбучных 1280–1440.
3. Порог 1600 же включает широкие колонки: `--nav-a: 190; --nav-b: 240; --viewer-max: 960`. Ниже — `170/220` и потолок 900.
4. Проверить, что при этом поиск (U2-07) получил ширину 450+ px и не сломал сетку.

**Приёмка (замеры):** 1024 — ≥ 500; 1280 — ≥ 700 (сейчас 523); 1440 — ≥ 850 (сейчас 683); 1920 — 960 при потолке макета 1760 (сейчас 780); на 769–1599 панель закладок заменена FAB, колонки дают ≥ 130 px внутренней ширины папкам.
#### U2-09 · Седьмая плитка хаба — P2, 0,2 дня

**Симптом:** «выровнять плитку „Опрос“ по ширине 3 плиток».

**Что сделать:** `.menu-item:last-child { grid-column: 1 / -1; }` на ≥769 px; для такой широкой карточки — горизонтальная компоновка (иконка + заголовок слева, описание справа) или центрирование, чтобы она не выглядела пустой. Альтернатива: добавить 8-ю плитку — но это контентное решение, не техническое.

**Приёмка:** на 1440 px третий ряд занят одной карточкой во всю ширину, высота ряда не скачет; на мобиле поведение не меняется (там плитки и так во всю ширину).

#### U2-10 · Подвал по ширине страницы — P2, 0,2 дня

**Симптом:** «сделать блок с контактами полноценным подвалом сайта по ширине страницы».

**Причина:** `.site-footer { max-width: 1000px }` (`style.css:1683-1695`), шапка — 1200 px (`index.html:37`), сетка плиток — 1000 px (`:142`). Три разных ширины на одном экране.

**Что сделать:** привести к одной ширине страницы (1200 px, как шапка), поля 20 px, скругление сохранить. Если нужен «настоящий» подвал во всю ширину — делать full-bleed с внутренним контейнером 1200; но тогда он перестанет совпадать с сеткой плиток, поэтому по умолчанию — 1200.

**Приёмка:** левый и правый край подвала совпадают с шапкой на 1024/1440/1920; на мобиле — с полями body (10 px).

| FAB на одной высоте (U2-06) | ✔ | ✔ | ✔ | ✔ | ✔ | ✔ | ✔ | — |

| Подвал = шапка (U2-10) | ✔ | ✔ | ✔ | ✔ | ✔ | ✔ | ✔ | ✔ |

Сценарии, которые прогоняются всегда:

1. **Первый визит без кэша** (чистый профиль) — везде есть скелетон, нет «пустоты».
2. **Кэш есть, Supabase заблокирован** — контент из кэша, нет ложного офлайна.
3. **Wi-Fi выключен** — честная плашка «автономный режим».
4. **Медленная сеть** (Chrome Throttling «Slow 3G») — первый экран появляется ≤ 6 с.
5. **Тач-устройство** — нет квадратной подсветки, тултипы не под кнопками.
